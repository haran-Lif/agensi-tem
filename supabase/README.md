# Supabase 로그인 연결

## 1. 테이블과 RLS 생성

Supabase Dashboard의 SQL Editor에서 `001_auth_profiles.sql` 전체를 실행합니다.

로그인 계정 연결이 끝나면 DBeaver 또는 SQL Editor에서
`002_operational_access.sql`을 실행합니다. 이 SQL은 기존 운영 테이블의
HTML 조회·저장 권한과 프로젝트별 접근 정책을 설정합니다.

마지막으로 `003_app_settings.sql`을 실행합니다. 이 SQL은 인당 생산량
기준의 근무일수와 버퍼를 DB에 저장하는 설정 테이블을 추가합니다.

기존 DB에 `003_app_settings.sql`만 적용되어 있거나 회사 버퍼 저장이
반영되지 않는 경우 `011_app_settings_save_rpc.sql`을 추가로 실행합니다.
이 SQL은 `projectBuffer`, `companyBuffer` 값을 보정하고 HTML에서 설정을
안정적으로 저장할 수 있는 `app_save_setting()` RPC를 추가합니다.

이어서 `004_output_rule_sla.sql`을 실행합니다. 이 SQL은 프로젝트별
업무/산출물 유형에 서로 다른 SLA 영업일 기준을 저장합니다. 유형별 값이
활성화되지 않았으면 프로젝트 기본 SLA를 사용하고, 활성화된 `0`은 당일
완료 기준입니다.

마지막으로 `005_output_worker.sql`을 실행합니다. 이 SQL은 한 업무를
여러 작업자가 나누어 처리한 경우에도 산출물별 작업자를 보존하여
`산출물 누적`과 `작업자별 산출물` Excel 집계를 모두 만들 수 있게 합니다.

이어서 `006_worker_task_access.sql`을 실행합니다. 이 SQL은 `worker`
권한과 `worker_task_status` 테이블을 추가하고, 실무자 계정에는 본인이
담당자로 지정된 업무와 산출물만 조회되도록 RLS 정책을 변경합니다.
실무자의 개인 처리 상태는 전체 업무 상태와 분리하여 저장됩니다.

마지막으로 `007_account_admin_rpc.sql`을 실행합니다. 이 SQL은 관리자
계정이 HTML의 계정·권한 관리 메뉴에서 Supabase Auth 계정을 생성하고,
권한·담당 프로젝트·비밀번호를 수정할 수 있게 하는 관리자 전용 RPC를
추가합니다.

업무별 공수 보정과 단축근무 기능을 사용할 때는
`012_task_effort_reduced_work.sql`을 추가로 실행합니다. 이 SQL은
`task_history`에 개별 버퍼와 촬영 유형을, `employees`에 단축근무
기간·시간·1일 실근무시간을 저장하는 칼럼을 추가합니다.

퇴사자 관리 기능을 사용할 때는 `013_employee_resignation.sql`을 실행합니다.
이 SQL은 `employees`에 퇴사 사유 칼럼과 팀·기간 조회용 인덱스를 추가합니다.
퇴사 처리는 인원을 삭제하지 않으므로 과거 업무·프로젝트 이력이 유지됩니다.

기존 DB의 저장 오류를 한 번에 보완하려면 마지막으로
`014_db_save_reliability.sql`을 실행합니다. 이 SQL은 현재 HTML이 사용하는
확장 칼럼을 확인·보강하고, `operator_output_admin` 권한이 담당 프로젝트의
업무 템플릿과 변경 이력을 저장할 수 있도록 RLS 정책을 맞춥니다.
실행 후에는 HTML을 새로고침하고 다시 로그인합니다. 상세 진단은
`03_DB_저장실패_점검쿼리.txt`를 사용합니다.

계정·직원·프로젝트 권한 입력을 통합한 화면을 사용할 때는 이어서
`015_team_project_account_flow.sql`을 실행합니다. 운영자와 실무자의 프로젝트
접근 범위는 `계정의 직원명 및 팀 → 프로젝트 작업 세팅의 진행 팀`으로 자동
계산됩니다. 실무자 작업함은 이 프로젝트 범위 안에서도 업무 또는 산출물의
담당자로 지정된 건만 표시합니다. 고객 포털은 기존 명시적 프로젝트 지정을
유지합니다.

프로젝트별 공지사항, 공통사항, 작업 가이드를 `업무 자료` 메뉴에서 관리하려면
`016_work_resources.sql`을 실행합니다. 자료 조회는 계정의 프로젝트 접근 범위를
따르며, 관리자와 운영자 권한만 등록·수정·삭제할 수 있습니다. 실무자는 담당
프로젝트의 자료를 조회할 수 있습니다.

실무자가 `내 작업` 수정 팝업에서 상태와 결과물 종류·수량을 저장하게 하려면
`017_worker_task_output_edit.sql`을 실행합니다. 실무자에게 배정된 업무만
`task_history` 상태와 `output_history` 상세를 변경할 수 있으며, 관리자 전용
개별 버퍼와 담당자·일정 정보는 화면과 권한 양쪽에서 계속 제한됩니다.

수익성 화면에서 프로젝트별 손해 구간과 적자 진입 시점을 계산하려면
`018_project_profitability.sql`을 실행합니다. 프로젝트 구성에 입력한
`1인 월 원가`는 계약금과 동일하게 원 단위로 DB에 저장되며, HTML에서는
만원 단위로 입력하고 표시합니다.

프로젝트별 관리 인원을 실무 투입 인원과 분리해 계약 인원 및 손익 계산에
포함하려면 `019_project_management_people.sql`을 실행합니다. 관리 인원은
프로젝트 생산성에는 포함하지 않고 수익성의 총 투입 인원에만 포함합니다.

프로젝트 하나에 여러 팀과 팀 외 개별 지원 인원을 함께 배정하려면
`021_multi_team_individual_project_access.sql`을 실행합니다. 화면에서 선택한
모든 인원은 `project_members`에 저장되며 운영자·실무자의 프로젝트 및 업무 자료
접근 범위도 이 최종 투입 인원을 기준으로 계산됩니다. 고객 포털은 계속
`app_user_projects`에 명시적으로 지정된 프로젝트만 조회합니다.

운영·구축 프로젝트의 추가 계약 또는 확장 계약을 기존 계약과 묶어 관리하려면
`022_project_contract_extensions.sql`을 실행합니다. 프로젝트 구성에서 기준
프로젝트를 선택하면 각 계약은 별도 행으로 유지되고 수익성 화면에서는 같은
고객사·기준 프로젝트 묶음으로 표시됩니다.

통합 알림센터의 사용자별 읽음·처리 상태를 여러 PC에서 유지하려면
`024_notification_center.sql`을 실행합니다. 알림 본문은 업무 원장에서 실시간으로
계산하며 DB에는 사용자별 읽은 시각과 처리 완료 시각만 저장합니다. 실무자는
자기 업무, 운영자는 접근 가능한 프로젝트, 관리자는 전체 프로젝트 알림을 봅니다.
알림 조건은 관리자 화면에서 저장하며 기존 `app_settings`의
`notification_rules` 설정값을 사용합니다. Slack 등 외부 전송 기능은 포함하지 않습니다.

Excel 업무 업로드의 파일별 반영 이력과 최신 배치 되돌리기를 사용하려면
`025_upload_batch_history.sql`을 실행합니다. 실제 업무는 계속 `task_history`와
`output_history`에만 저장하며, 신규 테이블에는 파일별 처리 결과와 되돌리기용
업무 전후 스냅샷만 저장합니다. 적용 후 `025_적용확인.sql`로 확인할 수 있습니다.

업무별 SLA 귀책, 최초 SLA 완료 예정일, 일정 변경 사유와 변경 이력은
기존 `task_history.note`의 `APP_META` JSON에 저장합니다. 별도 테이블
추가 없이 HTML에서 저장하고 다시 불러옵니다.

## 업무 데이터 저장 원칙

- `task_history`: 업무 한 건당 한 행을 저장하는 업무 원장입니다.
- `output_history`: 한 업무에 포함된 산출물 종류와 수량을 저장하는 상세 테이블입니다.
- `projects`, `employees`, `teams`, `output_rules`: 관리자 기준정보이며 업무 Excel 업로드로 생성하거나 변경하지 않습니다.
- 대시보드와 월간·리소스 지표는 별도 집계 테이블에 저장하지 않고 업무 원장, 산출물 상세, 기준정보를 조합해 계산합니다.

## 2. 최초 관리자 사용자 생성

Authentication > Users > Add user에서 다음 형식으로 사용자를 생성합니다.

```text
Email: admin@users.agency-ops.app
Password: 직접 설정
Auto confirm user: 활성화
```

사용자가 입력하는 로그인 ID는 `admin`이며, 화면에서 내부 이메일로 자동 변환합니다.

## 3. 관리자 프로필 연결

`001_auth_profiles.sql` 하단의 최초 관리자용 `insert` SQL 주석을 해제해 실행합니다.
담당 프로젝트 목록은 현재 프로젝트명에 맞춰 수정할 수 있습니다.

## 4. 일반 사용자 규칙

사용자 ID가 `worker01`이면 Supabase Auth 이메일은 아래처럼 생성합니다.

```text
worker01@users.agency-ops.app
```

HTML의 `계정·권한 관리`에서는 계정명과 권한만 생성합니다. 이어서
`회사 업무 그룹 > 인원 등급 리스트`에서 해당 계정에 직원명, 팀, 세부그룹,
포지션, 등급을 연결합니다. 운영자와 실무자의 프로젝트 접근 범위는
`프로젝트 작업 세팅`에서 같은 팀에 매칭된 진행 프로젝트로 자동 계산됩니다.
`app_user_projects`의 명시적 프로젝트 지정은 고객 포털 계정에만 사용합니다.

업무 등록 시에는 프로젝트 진행 팀에 소속된 직원만 담당자로 선택할 수 있습니다.
담당자로 지정된 실무자는 로그인 후 `내 작업`에서 본인에게 할당된 업무만
확인하고 처리 상태를 변경합니다.

## 업무 자료

`016_work_resources.sql`은 업무 자료 테이블과 다중 이미지용 비공개 Storage
버킷을 생성합니다. 본문은 `text`, 이미지 경로는 `image_paths`에 저장하며,
이미지 원본은 `work-resource-images` 버킷에 프로젝트 권한 범위로 저장됩니다.

## 보안

- HTML에는 Publishable Key만 포함합니다.
- Secret Key, service_role 키, DB 비밀번호는 포함하지 않습니다.
- 업무 데이터 테이블에도 사용자 권한에 맞는 RLS 정책이 별도로 필요합니다.
