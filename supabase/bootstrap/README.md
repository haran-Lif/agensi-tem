# 새 프로젝트 설치 가이드

이 폴더는 **기존 운영 데이터를 복사하지 않고 관제 시스템 v143을 새 프로젝트에 설치**하기 위한 패키지입니다. 기존 프로젝트·직원·업무·평가·비밀번호는 포함하지 않습니다.

## 1. 새 Supabase 프로젝트 준비

별도 Supabase 프로젝트를 만들고 해당 프로젝트의 SQL Editor를 엽니다. 기존 운영 DB에는 실행하지 마세요. Auth/Storage가 준비된 Supabase 환경이 필요합니다. 일반 PostgreSQL만으로는 Auth/Storage 서비스까지 제공하지 않습니다.

1. `001_schema.sql` **전체** 실행: 테이블 23개, 함수 12개, 정책 46개 및 비공개 이미지 버킷 2개 생성.
2. `002_defaults.sql` **전체** 실행: 공통 기본 설정 4개 생성. 반복 실행해도 이미 수정한 값을 덮어쓰지 않습니다.
3. 최초 관리자는 아래 절차로 등록합니다.
4. `004_verify.sql` 조회 결과가 모두 `ok = true`인지 확인합니다.

과거 `supabase/001~027` 스크립트를 추가로 일괄 실행하지 마세요. 기존 설치를 위한 변경 이력이며, 여기의 통합 스키마에 최종 정의를 반영했습니다. 스키마 설치는 한 번만 실행하며, 기존 앱 객체가 있으면 중단하고 덮어쓰지 않습니다. SQL 오류 시 같은 세션에서 `ROLLBACK;` 후 원인을 확인하세요.

## 2. 최초 관리자 생성

1. 새 Supabase의 Authentication → Users에서 사용자를 생성합니다.
2. 로그인 ID가 `admin`이면 이메일은 **admin@users.agency-ops.app**로 지정하고 이메일 확인 완료 상태로 생성합니다. 비밀번호는 직접 정합니다.
3. 생성된 사용자 UUID를 복사합니다.
4. `003_first_admin.sql`을 SQL Editor에 복사하고 맨 위 `admin_user_id`, `admin_login_id`, `admin_display_name`을 바꾼 뒤 전체 실행합니다. 템플릿 원본에는 실제 UUID/비밀번호를 기록할 필요가 없습니다.
5. 앱에서 `admin`과 설정한 비밀번호로 로그인합니다. 최초 관리자 이후에는 앱의 계정 관리 기능을 사용합니다.

이메일 도메인은 현재 앱과 계정 생성 RPC의 내부 로그인 규약입니다. 실제 메일 발송용 주소가 아닙니다. 기본값을 유지하세요. 도메인을 바꾸려면 연결 설정뿐 아니라 `app_admin_upsert_auth_account`의 이메일 생성 규칙과 생성 계정 주소도 함께 바꿔야 합니다. 외부 이메일 기반 비밀번호 복구는 별도 설계 항목입니다.

## 3. 프런트엔드 연결 및 실행

저장소 루트에서:

```sh
cp supabase-config.example.js supabase-config.js
```

생성된 `supabase-config.js`에 **새 프로젝트 URL과 publishable key**를 입력합니다. 예전 DB 주소를 복사하지 마세요. service-role/secret 키는 입력하지 않습니다. 이 파일은 Git에서 제외됩니다.

```sh
python3 -m http.server 8000
```

브라우저에서 `http://localhost:8000`을 엽니다. 실제 운영은 HTTPS 정적 호스팅에 배포합니다. 빌드 과정은 필요하지 않으며 루트 HTML/JS/CSS와 vendor 디렉터리를 함께 배포합니다. SQL·테스트·백업 자료는 웹 호스팅 대상에서 제외해도 됩니다. Supabase 프로젝트의 Auth URL 설정도 배포 주소에 맞게 확인합니다.

## 4. 관리자 최초 설정 순서

1. 회사명·로고 등 브랜딩 설정.
2. 팀·그룹, 직위 등록 후 직원 등록. 기본 직원/가상 계정은 자동 생성하지 않습니다.
3. 고객사·프로젝트 및 계약 기간, 프로젝트 투입 인원 설정.
4. 직원 계정 생성 및 역할·소속 확인. 직원명과 로그인 표시명이 연결 기준이므로 동일하게 설정하고 중복 이름을 피합니다.
5. 프로젝트별 산출물 템플릿과 기준공수 등록. 단가 및 산출물은 프로젝트마다 달라 미리 넣지 않습니다.
6. 작업 월별 W/D와 일·월 목표 공수 설정. 기본 21일은 공휴일 계산 결과가 아닌 초기 대체값입니다. 앱 내 공휴일 목록은 2026년 기준이므로 다른 연도는 월별 W/D를 직접 확인·등록해야 합니다.
7. 테스트 업무 1건으로 완료 예정일 기준 일간 현황, 담당자 배정, 결과물 수량과 공수를 확인한 후 사용합니다.

기본 설정은 생산성 목표 100%/100%, 수동 근무일 달력(빈 월 목록), 회사명 자리표시자, 기본 알림 규칙입니다. 업무 상태·촬영 유형·등급 등의 기본 목록은 앱 상수로 제공됩니다. 현재 앱이 조회하지 않는 code_master에는 추측한 코드 데이터를 넣지 않습니다.

## 5. 접근 권한과 첨부파일

- 업무 자료 이미지: `work-resource-images`, 비공개, 파일당 10 MiB.
- 평가 자료 이미지: `employee-review-images`, 비공개, 파일당 10 MiB, 관리자 정책.
- 허용 형식: JPEG, PNG, WebP, GIF.
- 공개 일간: `daily-public.html`. 프로젝트의 공개 설정은 기본 false입니다. 공개를 켠 프로젝트의 작업자명/날짜/공수 집계만 익명 RPC로 제공됩니다.
- 새 설치본은 익명 사용자에게 업무 테이블 조회 권한을 부여하지 않습니다.

## 운영 스냅샷과의 의도된 차이

- 운영 데이터/기존 ID/시퀀스 현재값을 가져오지 않습니다.
- 계정 생성 RPC는 최종 소스 `supabase/007_account_admin_rpc.sql`을 사용합니다. 운영 스냅샷의 이전 함수와 달리 generated `confirmed_at`에 쓰지 않고 `operator_output_admin`을 지원하며 프로필 PK 충돌 처리를 명확히 합니다.
- 운영 스냅샷의 광범위한 기본 grants를 그대로 복제하지 않고, 앱 정책에 필요한 CRUD와 함수 실행만 부여합니다. 모든 앱 테이블에 RLS를 켭니다. 정책이 없는 레거시 업로드 테이블 및 `Project`는 브라우저 권한을 부여하지 않습니다. 서버용 service_role에는 권한을 유지합니다.
- 이미지 버킷은 최종 소스의 정의로 생성합니다. 스냅샷에는 버킷 데이터가 없었습니다.

## 검증 범위

2026-11-27 로컬 PGlite 0.6.0(PostgreSQL WASM)에서 통합 SQL을 수정 없이 실행했습니다. Auth 사용자 테이블/uid 및 Storage 테이블/폴더 함수는 최소 SQL 테스트 fixture를 사용했습니다.

검증: 빈 DB 설치, 테이블 컬럼/제약조건 일치, seed 반복 실행과 설정 보존, 기존 설치 덮어쓰기 차단, 관리자 템플릿 보호, 관리자 등록, 계정 RPC 생성/수정, 설정 RPC, 업무 등록, 평가 등록 트리거, 익명 권한 제한, 비관리자 평가/저장소 제한, 공개 전/후 일간 집계와 날짜·공수 확인. 기존 앱 회귀 테스트도 실행합니다.

**실제 호스팅 Supabase의 GoTrue 로그인·PostgREST·Storage HTTP 업로드는 이 로컬 검증에 포함되지 않습니다.** 새 프로젝트 연결 후 관리자/실무자 로그인, 데이터 저장·재조회, 이미지 업로드·보기, 역할별 접근 및 공개 일간을 확인하세요. 계정 RPC는 현재 앱처럼 Auth DB에 직접 계정을 생성하므로 새 Supabase Auth 환경에서 실제 계정 로그인까지 확인해야 합니다. 기존 운영 DB에는 어떤 설치나 테스트도 실행하지 않았습니다.

재검증:

```sh
python3 scripts/build-bootstrap.py
npm ci --prefix tests/bootstrap
npm test --prefix tests/bootstrap
node --test tests/*.test.cjs
```

생성기와 스냅샷을 바꿀 경우 SQL을 재생성하고 테스트를 다시 실행하세요.
